## Architectural decisions

- **โปรเจกต์:** Next.js App Router + React + TypeScript รวมหน้าเว็บและ API ในโปรเจกต์เดียว ใช้ Node.js LTS ที่รองรับกับ Next.js รุ่นที่เลือก
- **Routes:** หน้าเข้าสู่ระบบ `/login`, ภาพรวม `/`, รายการ `/records`, สวน `/gardens` และรายละเอียด `/gardens/:id`; API ใช้ namespace `/api/v1` ฟอร์ม/รายละเอียดรายการเป็นป๊อปอัปหรือแผงเลื่อน
- **ข้อมูล:** Supabase PostgreSQL ตั้งแต่พัฒนา ทดสอบ และใช้งานจริง เก็บ SQL migrations มีเวอร์ชัน แบบ SQLite เดิมเป็นข้อมูลอ้างอิงกติกา ต้องแปลงและตรวจใหม่ก่อนใช้
- **Key models:** gardens, parties, ledger_entries, sale_deductions, expense_payments, expense_allocations, receipt_files, receipt_links, ocr_drafts, audit_events และ idempotency_requests ตามสเปก
- **การคำนวณ:** เงินเก็บเป็นสตางค์ จำนวน/อัตราระบุหน่วยชัดเจน ใช้ integer/decimal arithmetic ปัดครึ่งขึ้นตอนจบ รักษาความแม่นยำเมื่อส่ง JSON; backend ตรวจและคำนวณใหม่ทุก write
- **Transactions:** ขายพร้อมค่าแรง การจ่าย/ยกเลิกการจ่าย และการแบ่งส่วนกลางต้อง atomic ใน PostgreSQL ใช้ locking/constraints ป้องกันคำขอพร้อมกัน ไม่ถือว่าหลาย HTTP calls เป็น transaction เดียว
- **บัญชี:** เจ้าของคนเดียว ใช้ username + password ผูกกับ Supabase Auth ฝั่งเซิร์ฟเวอร์ ไม่ให้ผู้ใช้กรอกอีเมล ปิดสมัครสมาชิกทั่วไป จำการเข้าสู่ระบบบนเครื่องส่วนตัว 30 วัน ผู้ดูแลช่วยตั้งรหัสใหม่และยกเลิก session เดิม
- **รูป:** Supabase private Storage เก็บต้นฉบับพร้อม metadata/checksum ในฐาน เปิดอ่านหลังตรวจเจ้าของ รองรับ JPEG/PNG/WebP/HEIC/HEIF ตามสเปก ต้องพิสูจน์ขนาด upload และการแปลงภาพกับ runtime ของโฮสต์
- **ความถูกต้องทุกขั้น:** ตรวจ owner session, RLS/สิทธิ์รูป, idempotency ของ write, validation และ audit ตั้งแต่เพิ่มแต่ละความสามารถ การแก้ไขใช้ expected version เพื่อป้องกันแท็บเก่าทับข้อมูล
- **การทดสอบ:** ตรวจพฤติกรรมผ่าน Next.js API กับ PostgreSQL จริงและ migrations ในสภาพแวดล้อมทดสอบแยก ใช้ Supabase local/test สำหรับ Auth/Storage เสริม browser tests เฉพาะ flow ที่ API พิสูจน์ไม่ได้ ผลทดสอบต้นแบบเดิมไม่ใช่ผลตรวจระบบใหม่
- **โฮสต์:** เน้นแพ็กเกจฟรีที่อนุญาตงานสวนและรองรับ Next.js ฝั่งเซิร์ฟเวอร์ได้จริง Vercel เป็นตัวเลือกที่ต้องตรวจเงื่อนไข ยอมเปลี่ยนโฮสต์ได้ ไม่มีการอนุมัติบริการเสียเงินโดยอัตโนมัติ
- **สำรอง:** ฐานข้อมูลและรูปทุกวัน แยกจากระบบหลัก เป้าหมายข้อมูลสูญหายย้อนหลังประมาณไม่เกิน 24 ชั่วโมง ต้องเลือกตัวรัน ปลายทาง ระยะเก็บ และพิสูจน์กู้คืนจริง

## ลำดับและเกณฑ์ร่วม

ทุกขั้นส่งมอบพฤติกรรมที่สาธิตจากหน้าจอถึงฐานข้อมูลได้ พร้อมการทดสอบที่เกี่ยวข้อง ไม่แยกทำฐาน/API/UI จนจบทีละชั้น ขั้นที่ไม่ติด dependency เริ่มได้โดยไม่ต้องรอเลขก่อนหน้าทุกขั้น

ทุกฟอร์มมีสถานะบันทึก/สำเร็จ/ผิดพลาด คงข้อมูลเมื่อส่งไม่สำเร็จ ป้องกันกดซ้ำ และรองรับ reduced motion ตั้งแต่เริ่ม ขั้น 10 ตรวจรับรวมบน Safari และโฮสต์จริงอีกครั้ง

ตรวจเงื่อนไขโฮสต์ โควตา Supabase และความเป็นไปได้ของงานสำรองตั้งแต่เริ่มขั้นที่เกี่ยวข้อง พัฒนากับสภาพแวดล้อมทดสอบต่อได้ระหว่างรอสิทธิ์บริการ ห้ามใช้ข้อมูลจริงจนผ่านเกณฑ์ปล่อยใช้งาน

## Phase 1: เข้าสู่ระบบและจัดการสวน

**สถานะ: เสร็จและผู้ใช้รับงานแล้ว** วันที่ 21 ตุลาคม 2569 ผู้ใช้ยืนยันว่าเฟสแรกทดสอบได้ปกติและสั่งให้ไปเฟสถัดไป มีบัญชี/session, สวน/ยอดยกมา, audit และ UI เขียว–ครีม/Three.js ทั้งมือถือและ desktop ดู [วิธีรันและผลตรวจ](../docs/development.md)

**สถานะ deploy ณ 21 ตุลาคม 2569:** [palm-ledger-nine.vercel.app](https://palm-ledger-nine.vercel.app) · Supabase `feotpdylvprtihgklndj` · code baseline `a010403` · deployment `dpl_GPnpxkFjCm9Aak4P32HdTs1No17G` เป็น Ready, migrations ผ่าน, owner configured ใช้ Session pooler และ TLS verification ไม่เก็บ connection string หรือค่าลับใน Git

**ผลตรวจ:** API integration 8/8, model เดิม 4/4, CLI/diagnostics 12/12, Chromium ของ production build 4/4, TypeScript/format/build ผ่าน ผู้ใช้รับงานเฟสแรกแล้ว ไม่ต้องสัมภาษณ์ brief หรือทำเฟส 1 ใหม่

**งานถัดไป:** เริ่มขั้น 2: บันทึกขายและแนบรูปบิล ตามคำสั่งผู้ใช้ ขั้น 2–10 ยังไม่ implement

**หลักฐานที่ยังไม่ได้ยืนยันแยก:** ผู้ใช้ไม่ได้ระบุรายละเอียดอุปกรณ์หรือรายการตรวจ Safari/focus/keyboard ทุกข้อ และยังไม่มีหลักฐานจากผู้ช่วยยืนยันการปิด public signup บน hosted project เก็บรายการตรวจเฉพาะเหล่านี้ไว้ตรวจต่อในขั้น 10 โดยไม่อ้างว่าอัตโนมัติผ่านแล้ว และไม่ขวางการเริ่มขั้น 2 ที่ผู้ใช้อนุมัติ

**User stories:** 1–6, 8, 43–48

**ขึ้นกับ:** ไม่มี; ต้องมีสภาพแวดล้อม PostgreSQL/Auth ทดสอบเพื่อยืนยัน integration

### What to build

เจ้าของเข้าใช้ด้วยชื่อผู้ใช้และรหัสผ่าน เพิ่มสวน/ยอดยกมา ดูภาพรวมและรายละเอียดสวน แก้ไขชื่อ/ยอดยกมา เก็บสวนที่เลิกใช้เป็นประวัติ และให้ผู้ดูแลช่วยเมื่อเข้าบัญชีไม่ได้ เป็นเส้นทางแรกที่ใช้ Next.js API กับข้อมูลถาวรจริง

### Acceptance criteria

- [x] เข้าใช้โดยไม่กรอกอีเมล ไม่มีสมัครสมาชิกทั่วไป ผู้ไม่มีสิทธิ์อ่าน/เขียนข้อมูลผ่าน API หรือเข้าถึง Supabase โดยตรงไม่ได้ (ตรวจ local Auth/REST)
- [x] เพิ่มสองสวนพร้อมยอดยกมา ภาพรวมรวมยอดถูกต้อง รีเฟรชและเปิดจากอุปกรณ์อื่นด้วยบัญชีเจ้าของแล้วเห็นข้อมูลเดียวกัน
- [x] แก้ชื่อ/ยอดยกมาและเก็บสวนเป็นประวัติได้พร้อม audit ไม่ลบข้อมูลย้อนหลัง
- [x] จำการเข้าใช้ 30 วันบนเครื่องส่วนตัว ทดสอบ refresh/หมดอายุ/ออกจากระบบได้ และผู้ดูแลตั้งรหัสใหม่แล้ว session เดิมใช้ไม่ได้
- [x] migrations สร้างฐานทดสอบใหม่ได้ มี API integration tests และ production deployment apply migrations กับ hosted Supabase สำเร็จ
- [x] สร้างบัญชีเจ้าของบน hosted Supabase และผู้ใช้ยืนยัน login/ทดสอบเฟสแรกใช้งานได้ปกติ
- [ ] ตรวจยืนยัน hosted Auth settings/public signup แยกเป็นหลักฐาน — ตรวจต่อในขั้น 10
- [ ] บันทึกผล Safari จริงรวม focus/แป้นพิมพ์/reduced motion แยกเป็นหลักฐาน — ตรวจต่อในขั้น 10

## Phase 2: บันทึกขายและแนบรูปบิล

**สถานะ:** Implement และทดสอบผ่านใน isolated local stack; commit/push และตรวจ Vercel deployment อยู่ในขั้นตอนปิดงาน อ่าน [เอกสารส่งต่องาน](../docs/handoff-phase2.md) สำหรับรายละเอียดผล

**User stories:** 10–16, 39, 43

**ขึ้นกับ:** 1

### What to build

เจ้าของเลือกสวนและวันที่ กรอกบิลขาย น้ำหนัก ราคา และยอดหัก แนบรูปแล้วบันทึกเมื่อได้รับเงินเต็มจำนวน เปิดดูรายการ/รูปต้นฉบับและยอดสุทธิที่อัปเดตได้

### Acceptance criteria

- [x] ขาย 3,500 กก. × 5 บาท หัก 500 บาท → รายรับ 17,000 บาท ระบบตรวจรับเต็มจำนวนและคำนวณฝั่งเซิร์ฟเวอร์; ผ่าน integration test กับ PostgreSQL จริงใน local test stack
- [x] บิลซ้ำมีคำเตือนให้ตรวจและยืนยัน; retry คำขอเดิมได้รายการเดิม ส่วน idempotency key เดิมแต่ข้อมูลต่างกันได้ conflict
- [ ] อัปโหลดและเปิดรูปต้นฉบับจาก private Storage ได้เฉพาะเจ้าของ ตรวจชนิด/ขนาด/checksum ผ่าน integration test รวม HEIC fixture จริง; ยังไม่ได้ทดสอบภาพจากอุปกรณ์ iPhone โดยตรง
- [x] เมื่อการส่งหรืออัปโหลดล้มเหลว ค่าที่กรอกยังอยู่ ไม่มีรายรับซ้ำหรือรายการครึ่งชุด และ pending upload ที่ยังไม่ผูกจะหมดอายุใน 24 ชั่วโมงและถูกกวาดเมื่อมีการขอ upload URL ครั้งถัดไป

## Phase 3: รายจ่ายทั่วไป ค่าแรงรายวัน และปุ๋ย

**User stories:** 23–29, 32, 43

**ขึ้นกับ:** 1, 2 สำหรับความสามารถแนบรูป

### What to build

บันทึกรายจ่ายพร้อมสวน วันที่ ผู้รับเงิน รูปและหมายเหตุ จำชื่อ/อัตราคนงาน รองรับครึ่งวันและค่าปุ๋ยที่ใช้จริง เลือกจ่ายครบ/บางส่วน/ยังไม่จ่ายพร้อมประวัติการจ่ายครั้งแรก

### Acceptance criteria

- [ ] ค่าแรงครึ่งวันที่ 500 บาท/วัน → 250 บาท จำอัตราเดิมและเปลี่ยนเฉพาะรายการได้
- [ ] ใช้ปุ๋ย 4 กระสอบ × 800 บาท → รายจ่าย 3,200 บาท ไม่มีการลงซื้อหรือสต็อกปุ๋ยที่ยังไม่ใช้
- [ ] จ่ายครบ/บางส่วน/ยังไม่จ่ายให้ยอดค้างถูกต้อง รายจ่ายลดสุทธิครั้งเดียวเมื่อเกิดรายการ การจ่ายครั้งแรกบันทึกใน transaction เดียวกัน
- [ ] ชนิดรายจ่าย หน่วย ยอดติดลบ/ยอดจ่ายเกิน และ retry ถูกตรวจผ่าน API กับฐานจริง การแนบรูปใช้กติกา private Storage เดียวกับบิลขาย

## Phase 4: ค่าแรงทีมที่ผูกกับบิลขาย

**User stories:** 20–22, 25, 39

**ขึ้นกับ:** 2, 3

### What to build

เลือกทีมและอัตราต่อตันจากฟอร์มขาย เสนอค่าแรงจากน้ำหนัก เจ้าของตรวจ/แก้ฐานน้ำหนักหรืออัตราได้ แล้วสร้างรายรับและค่าแรงทีมค้างจ่ายพร้อมกัน รวมถึงลงค่าแรงตามผลผลิตแยกได้

### Acceptance criteria

- [ ] 3,500 กก. × 1,000 บาท/ตัน → ค่าแรงทีม 3,500 บาท และจำชื่อ/อัตราทีมสำหรับครั้งถัดไป
- [ ] ปรับน้ำหนักคิดค่าแรงต่างจากน้ำหนักขายได้ โดยเก็บฐานคำนวณและผลลัพธ์ชัดเจน
- [ ] ขายพร้อมค่าแรงสำเร็จทั้งชุดหรือไม่บันทึกทั้งคู่ เมื่อขั้นใดล้มเหลวไม่มีข้อมูลครึ่งชุด และ retry ไม่สร้างซ้ำ
- [ ] เปิดตรวจการเชื่อมบิลกับค่าแรงได้ ค่าแรงเป็นยอดรวมทีม ไม่เพิ่มการแบ่งให้สมาชิกทีม

## Phase 5: หนี้เดิม การจ่าย และแก้ยอดจ่ายผิด

**User stories:** 7, 30–33, 38, 49

**ขึ้นกับ:** 3; ตรวจรับกับค่าแรงทีมจาก 4 เพิ่มเมื่อพร้อม

### What to build

ลงหนี้ก่อนเริ่มระบบ ดูยอดค้างตามรายการ/คน/ทีม/ร้าน จ่ายหลายครั้งได้ตามสะดวก และแก้การจ่ายผิดด้วยการยกเลิกเฉพาะครั้งเดิมแล้วบันทึกใหม่ โดยประวัติยังอยู่

### Acceptance criteria

- [ ] ยอดยกมา 5,000 บาทพร้อมหนี้เดิม 1,000 บาท → สุทธิยัง 5,000 บาทและค้าง 1,000 บาท
- [ ] หนี้ 10,000 บาท จ่าย 6,000 แล้ว 4,000 → ค้าง 0 บาท ยอดสุทธิไม่ถูกหักซ้ำ ไม่มีการบังคับรอบจ่ายรายเดือน
- [ ] คำขอจ่ายพร้อมกันที่รวมเกินยอดค้างสำเร็จได้เฉพาะยอดที่ไม่เกิน ที่เหลือได้ conflict โดยข้อมูลไม่เสีย
- [ ] กรอกจ่ายผิด 5,000 บาทแล้วยกเลิก → ค้างกลับเป็น 10,000 บาท; ลงใหม่ 500 บาท → ค้าง 9,500 บาท เก็บประวัติและ retry ยกเลิกไม่เพิ่มค้างซ้ำ

## Phase 6: รายจ่ายส่วนกลางและแบ่งเข้าสวน

**User stories:** 9, 34–36

**ขึ้นกับ:** 3, 5

### Acceptance criteria

- [ ] ส่วนกลางที่ยังไม่แบ่งหักจากยอดรวมหนึ่งครั้ง และแสดงแยกจากยอดรายสวนอย่างชัดเจน
- [ ] ส่วนกลาง 1,000 บาท จ่ายแล้ว 333.33 บาท แบ่ง A 400 บาท/B 600 บาท → ต้นทุนรวมยัง 1,000 บาทและจ่ายรวมยัง 333.33 บาท
- [ ] ยอดแบ่งต้องครบและทำใน transaction เดียว ปฏิเสธยอดไม่ครบ/เกินโดยไม่เปลี่ยนข้อมูลบางส่วน
- [ ] การแบ่งที่มีเศษสตางค์ไม่ทำให้ยอดจ่ายรายสวนติดลบหรือเกินต้นทุน ประวัติเดิมไม่ถูกคัดลอกเป็นการจ่ายใหม่ และแก้ชุดแบ่งแล้วผลรวมยังถูกต้อง

## Phase 7: แก้ไขรายการ รายงาน และ CSV

**User stories:** 8, 30, 37–40, 43

**ขึ้นกับ:** 4, 5, 6

### What to build

ค้น/กรองรายการ เปิดรายละเอียดเพื่อแก้ไขหรือยกเลิกพร้อมผลกระทบและ audit ดูยอดรายสวน/รวม แล้วส่งออก CSV ตามตัวกรองได้

### Acceptance criteria

- [ ] แก้จาก version เก่าได้ conflict โดยไม่ทับข้อมูลใหม่ ห้ามแก้รายจ่ายต่ำกว่ายอดจ่ายที่มีผล
- [ ] แก้/ยกเลิกบิลขายแสดงค่าแรงที่เกี่ยวข้องให้ตรวจแยก ไม่เปลี่ยนตามเงียบ ๆ; ยกเลิกรายจ่ายที่มีประวัติจ่ายต้องยืนยันผลกระทบและเก็บ audit
- [ ] ตัวอย่างสวน A สุทธิ 28,000 บาท/B สุทธิ 14,800 บาท → รวม 42,800 บาท กรองวันที่ไม่บวกยอดยกมาซ้ำและระบุว่ายอดค้างเป็นสถานะปัจจุบัน
- [ ] ตัวกรองสวน/วันที่/ประเภทตรงกับรายการและรายงาน CSV อ่านภาษาไทยได้และป้องกันข้อความกลายเป็น spreadsheet formula

## Phase 8: สำรอง กู้คืน และย้ายข้อมูลต้นแบบ

**User stories:** 41, 42

**ขึ้นกับ:** 7

### What to build

เจ้าของสร้างชุดสำรองรวมรูป ตรวจตัวอย่างก่อนกู้คืน หรือเลือก JSON ต้นแบบเพื่อย้ายข้อมูลจริง โดยเทียบสวน รายการ ประวัติ รูป และยอดก่อนสลับใช้งาน

### Acceptance criteria

- [ ] สำรองฐานและรูปพร้อม manifest/checksum แล้วกู้ในสภาพแวดล้อมใหม่ได้ครบ รวมข้อมูลเชื่อมบัญชีที่จำเป็นต่อการเข้าถึง
- [ ] ชุดสำรองเสียหรือรูปขาดไม่แทนข้อมูลเดิม กู้คืนลงพื้นที่ใหม่และตรวจผลก่อนสลับใช้งาน
- [ ] JSON จากต้นแบบแยกข้อมูลตัวอย่าง/ข้อมูลจริง ตรวจ version และ duplicate IDs พร้อม preview ก่อนยืนยัน
- [ ] paid เดิมที่ไม่มี payment rows ถูกแปลงโดยยอดสุทธิและค้างก่อน/หลังตรงกัน และรูปต้นฉบับที่นำเข้าตรวจเปิดได้

## Phase 9: สำรองอัตโนมัติรายวัน

**User stories:** 41, 50

**ขึ้นกับ:** 8 และตัวรัน/ปลายทางสำรองที่พร้อมใช้งานและตรวจเงื่อนไขแล้ว

### What to build

งานสำรองฐานและรูปทำทุกวันโดยผู้ใช้ไม่ต้องกดเอง เก็บแยกจากระบบหลัก เห็นเวลาสำเร็จล่าสุด และผู้ดูแลรับแจ้งเมื่อมีปัญหา พร้อมขั้นตอนกู้คืนที่พิสูจน์แล้ว

### Acceptance criteria

- [ ] เลือกตัวรัน ปลายทาง และระยะเก็บตามโควตา/สิทธิ์ใช้งานที่ตรวจแล้ว โดยไม่ผูกกับ process บนเว็บที่อาจหยุดหรือ redeploy
- [ ] สำรอง PostgreSQL และรูปเป็นชุดสอดคล้องกันทุกวัน เก็บแยกจากระบบหลัก และไม่ถือว่าฐานข้อมูลสำรองครอบคลุม Storage/Auth โดยอัตโนมัติ
- [ ] แสดงเวลาสำเร็จล่าสุด แจ้งผู้ดูแลเมื่องานล้มเหลวหรือจุดสำรองเก่าเกิน 24 ชั่วโมง และตรวจการรันซ้ำไม่ทำชุดสำรองเสีย
- [ ] จำลองกู้คืนจากสำรองอัตโนมัติในพื้นที่แยก เทียบยอด รูป และการเข้าใช้บัญชีได้จริง เป้าหมายสูญเสียข้อมูลย้อนหลังไม่เกินประมาณหนึ่งวัน

## Phase 10: อ่านบิลและตรวจรับก่อนใช้งานจริง

**User stories:** 1, 3, 17–19, 43–47; ตรวจรับรวมทุกเรื่องจากขั้น 1–9

**ขึ้นกับ:** OCR เริ่มได้หลัง 2, 4 และมี provider/credentials ที่ได้รับสิทธิ์จริง; การปล่อยระบบครบสเปกต้องผ่าน 1–9 และเกณฑ์ตรวจรับทั้งหมดของขั้นนี้

### What to build

อ่านรูปบิลเป็นฉบับร่างให้เจ้าของตรวจแก้ก่อนลงรายการ จากนั้นตรวจ flow รวมบน iPhone/Safari และโฮสต์ที่เลือกจริง ให้ยืนยันได้ทั้งความสะดวก ความถูกต้อง และการกู้ข้อมูล แบ่งตรวจงาน OCR กับตรวจรับการใช้งานเป็นรายการย่อยภายในขั้นนี้ได้

### Acceptance criteria

- [ ] อ่านบิลแล้วได้ draft ไม่ลงรายรับก่อนยืนยัน ช่องไม่มั่นใจต้องให้ตรวจ อ่านล้มเหลวกลับไปกรอกเองได้ และ retry/ยืนยันซ้ำไม่สร้างขายหรือค่าแรงซ้ำ
- [ ] ใช้ provider และโฮสต์ที่ตรวจสิทธิ์/โควตา/ค่าใช้จ่ายแล้ว โฮสต์รองรับ Next.js API, cookies, PostgreSQL connection และรูป iPhone ได้จริง หาก Vercel Free ไม่รองรับงานนี้เลือกโฮสต์อื่นที่ผ่านเงื่อนไข
- [ ] Safari จริงที่ประมาณ 390 px ผ่าน flow เริ่มสวน → ขายพร้อมรูป/ค่าแรง → ปุ๋ย → จ่ายบางส่วน/แก้จ่ายผิด → ดูยอด → สำรอง; ปุ่มไม่ถูกคีย์บอร์ดบัง ไม่มี overflow และ focus/reduced motion ถูกต้อง
- [ ] จำลอง network ช้า/ล้มเหลว ฟอร์มยังอยู่และไม่รายงานสำเร็จก่อน backend ตอบ ตรวจ username/session/การช่วยตั้งรหัสใหม่และการเข้าถึงรูปจริง
- [ ] redeploy แล้วฐานและรูปยังอยู่ migrations ไม่ลบข้อมูลเดิม สาธิตสำรอง/กู้คืนจริงผ่าน และไม่มีข้อบกพร่องระดับ P0/P1/P2 ค้างก่อนเรียกว่า production-ready

## จุดส่งมอบและสิ่งที่ยังต้องตรวจ

- **หลังขั้น 8:** มีความสามารถกรอกเองพร้อมสำรอง/กู้คืนสำหรับทดสอบรับงาน ยังต้องผ่านสำรองอัตโนมัติและการตรวจปล่อยใช้งานก่อนใช้เป็นระบบจริง
- **ขั้น 9 ทำได้โดยไม่ต้องรอ OCR:** หาก provider ยังไม่พร้อม ให้เดินงานสำรองและตรวจ Safari/โฮสต์ของขั้น 10 ต่อได้ แต่ยังไม่ถือว่าระบบครบสเปก OCR
- **ก่อนใช้งานจริง:** ต้องผ่านทุกขั้นพร้อมเงื่อนไขโฮสต์ Supabase/OCR งานสำรอง และการกู้คืนที่ทดสอบแล้ว ไม่ใช้ผลทดสอบต้นแบบมาแทนผลตรวจระบบใหม่
- **ข้อมูลบริการที่ยังไม่ยืนยัน:** โฮสต์ สิทธิ์ใช้แพ็กเกจฟรี โควตา/การพักโครงการ ข้อจำกัดรูปและการแปลง HEIC/HEIF ค่าใช้จ่าย OCR ตัวรัน/ปลายทาง/ระยะเก็บสำรอง ต้องตรวจจากเอกสารปัจจุบันและการทดลองจริง เอกสารผู้ให้บริการเคยถูก proxy ปฏิเสธในรอบก่อน จึงยังไม่รับรองว่าทุกส่วนฟรี
- **นอกขอบเขต:** คงตามสเปก เช่น หลายผู้ใช้ สต็อกปุ๋ย ลูกหนี้ขาย การกระทบยอดธนาคาร และ offline sync ไม่มีการเพิ่มขอบเขตเหล่านี้ในแผน 10 ขั้น
