# ปรับ workflow บันทึกขาย — 21 ตุลาคม 2569

**สถานะรับงานล่าสุด:** ผู้ใช้ทดสอบแล้วให้ปิด Phase 2 โดยระบุว่า **OCR ได้ผลไม่ดี** ให้ปรับวิธี extraction ต่อใน Phase 10 ผลทดสอบ/เวลาที่บันทึกด้านล่างไม่ใช่หลักฐานว่าคุณภาพอ่านบิลหรือเป้าหมาย 1 นาทีผ่านการรับงานแล้ว งานถัดไป Phase 3 ดู [handoff](handoff-phase3.md)

ผู้ใช้ยืนยัน Phase 2 บนเว็บจริงแล้ว และสั่งให้ลดการกรอกด้วย flow **รูปบิลก่อน → รีวิว/แก้เฉพาะข้อมูลผิด → เลือกค่าแรงรายวันหรือรายน้ำหนัก** โดยมีเป้าหมายทำจบใน 1 นาที ผู้ใช้เลือก OCR ฟรีในเบราว์เซอร์ ไม่ใช้บริการ AI ที่ต้องมี API key

## สิ่งที่เปลี่ยน

1. หน้ารายการเริ่มด้วย “ถ่ายบิล” หรือ “เลือกรูปบิล” อัปโหลดต้นฉบับผ่าน signed upload ไป private Storage และอ่านรูปภาษาไทย/อังกฤษบนเครื่องผู้ใช้พร้อมกัน
2. แสดงภาพตัวอย่างที่ขยายได้คู่กับฉบับร่าง: วันที่ ผู้รับซื้อ เลขบิล น้ำหนักสุทธิ ราคาต่อกิโลกรัม และรายการหัก ตรวจช่องขาด/ความมั่นใจต่ำ และเทียบยอดสุทธิที่อ่านกับยอดคำนวณ แก้ก่อนยืนยันได้ทุกช่อง ถ้าอ่านไม่ได้/เกิน 45 วินาทีหรือกดข้าม ให้อ่านจากรูปและกรอกเองต่อได้
3. เลือกไม่มีค่าแรง, รายวัน หรือรายน้ำหนัก รายวันรองรับหลายคนและครึ่งวัน รายน้ำหนักใช้กิโลกรัมจากบิลและอัตราบาทต่อตัน โดยแก้ฐานน้ำหนักได้ จำสวน/ผู้รับซื้อครั้งล่าสุด และชื่อ/อัตราคนงาน/ทีมที่บันทึกสำเร็จแล้ว
4. แสดงรายรับ ค่าแรงค้างจ่าย และสุทธิหลังค่าแรงก่อนกดยืนยัน พร้อมยืนยันรับเงินขายเต็มจำนวน

ค่าแรงเกิดเป็น **ค่าใช้จ่ายค้างจ่าย** ใน transaction เดียวกับบิล ทำให้ยอดสุทธิรายสวน/รวมลดลงครั้งเดียว การจ่ายเงินจริงยังเป็นงาน Phase 5 รายการหักบนบิลกับค่าแรงเป็นคนละส่วน ถ้ามีค่าแรงถูกหักในบิลแล้วต้องตรวจไม่ลงซ้ำ

## แก้ OCR จากภาพบิลจริงที่ผู้ใช้แจ้ง (21 ตุลาคม 2569)

ภาพบิลสีน้ำเงินบนกระดาษยับมีฉากหลังและตารางหลายคอลัมน์ ทำให้ OCR เดิมข้ามน้ำหนักสุทธิ และ parser เดิมคาดว่าชื่อช่องกับค่าจะอยู่ในบรรทัดเดียว อีกทั้งราคาและยอดรวมอยู่แถวเดียวกันจึงเสี่ยงหยิบเลขท้ายแถวมาเป็นราคา ผลทดสอบภาพสังเคราะห์เดิมจึงยังไม่ครอบคลุมภาพนี้

- ตรวจขอบกระดาษ ตัดฉากหลัง จัดแนว ปรับความต่างแสงเฉพาะบริเวณ และลดเส้นตารางรวมถึงเส้นเอียง/เส้นประบนสำเนาสำหรับ OCR ต้นฉบับใน Storage คงเดิม
- อ่านแบบ sparse พร้อมตำแหน่งคำ แล้วประกอบแถวจริงก่อนแยกชื่อช่อง/ค่า รองรับสระและวรรณยุกต์ไทยที่ OCR แยกออก และอ่านราคา/ยอดรวมจาก label ของแต่ละช่อง
- เมื่อข้อมูลขาดหรือยอดไม่ตรง อ่านสำเนาสีซ้ำ หากยังขาดข้อมูลหรือยอดไม่ตรง ให้หาแถวที่ระบุ “น้ำหนักสุทธิ” แล้วอ่านเฉพาะช่องทางขวา ไม่ใช้ตัวเลขเขียนมือ น้ำหนักเข้า/ออก หรือเลขทะเบียนแทนน้ำหนักสุทธิ
- เครื่องหมายคั่นหลักพันจางอาจอ่านเป็นจุด ยอมแปลความใหม่เฉพาะเมื่อค่าน้ำหนักที่อ่านได้ × ราคาที่พิมพ์ ตรงกับยอดที่พิมพ์หลังรายการหักเท่านั้น พร้อมทำเครื่องหมายให้ตรวจน้ำหนัก ไม่คำนวณน้ำหนักขึ้นเองจากราคา/ยอดรวม
- ยังเป็น OCR ฟรีในเบราว์เซอร์และใช้โมเดลจากเว็บเดียวกัน ไม่เพิ่มบริการหรือ API key

ดาวน์โหลดต้นฉบับที่ผู้ใช้อัปโหลดแบบอ่านอย่างเดียวเพื่อตรวจซ้ำ แล้วอัปโหลดสำเนาเข้าระบบทดสอบ localhost ที่แยกจาก production ไม่ยืนยันสร้างรายการขาย ไม่เก็บรูปส่วนตัวหรือข้อความ OCR ใน Git เพิ่มบิลตารางจำลองสีน้ำเงิน/ฉากหลังมืดสำหรับ regression และ private-photo test แบบ opt-in ผ่าน `OCR_REAL_RECEIPT_PATH` (ตั้ง `OCR_REAL_EXPECTED_INVOICE` เพื่อตรวจเลขบิลแบบตรงตัวได้)

การทดสอบพบ nginx gateway ของ local stack จำกัดไฟล์ที่ 1 MiB จึงปรับเฉพาะ Storage route เป็น 12 MiB ให้ทดสอบต้นฉบับตามขอบเขต 10 MiB ได้ ปัญหานี้เป็นของระบบทดสอบ; ภาพ production ที่ผู้ใช้ส่งถูกเก็บไว้แล้ว

ผลรอบแรกที่แก้แล้ว: Chromium อ่าน **1,480 กก., 8.70 บาท/กก., 12,876.00 บาท, วันที่ 28/08/2569 และเลขบิลตรงภาพ** จากต้นฉบับจริงในประมาณ **22 วินาที** โดยไม่ส่ง POST สร้าง sale ชื่อบริษัท/ข้อความไทยที่อ่านไม่ชัดยังต้องให้ผู้ใช้ตรวจหรือกรอก ไม่รับรองว่าอ่านข้อความทุกส่วนถูกต้อง และยังไม่ถือว่าผ่านเป้าหมายหนึ่งนาทีบน iPhone/Safari จริง

ชุด regression เพิ่มตรวจแยกราคา/ยอดในแถวเดียว, แถวจาก bounding boxes, เครื่องหมายคั่นหลักพันผิด, ขอบกระดาษ/คอนทราสต์/เส้นเอียง และห้ามหยิบน้ำหนักเข้า/ออกมาแทนน้ำหนักสุทธิ ชุด browser ตรวจบิลตารางจำลองและรูปจริงโดยไม่ยืนยันสร้าง sale เพิ่มจาก workflow ค่าแรง/HEIC และ Three.js เดิม

รอบ production build ล่าสุด: รูปจริงเติมค่าหลักตรงภาพใน **14.95 วินาที** (รอบก่อนประมาณ 17–22 วินาที), บิลตารางจำลอง **6.27 วินาที**, flow ตัวอย่างเดิมตั้งแต่อัปโหลดถึงบันทึกพร้อมค่าแรง **7.82 วินาที**; เวลาเป็น Chromium บนเครื่องทดสอบ ไม่ใช่ผลจับเวลาบนอุปกรณ์ผู้ใช้
