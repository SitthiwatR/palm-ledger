# ปรับ workflow บันทึกขาย — 21 ตุลาคม 2569

ผู้ใช้ยืนยัน Phase 2 บนเว็บจริงแล้ว และสั่งให้ลดการกรอกด้วย flow **รูปบิลก่อน → รีวิว/แก้เฉพาะข้อมูลผิด → เลือกค่าแรงรายวันหรือรายน้ำหนัก** โดยมีเป้าหมายทำจบใน 1 นาที ผู้ใช้เลือก OCR ฟรีในเบราว์เซอร์ ไม่ใช้บริการ AI ที่ต้องมี API key

## สิ่งที่เปลี่ยน

1. หน้ารายการเริ่มด้วย “ถ่ายบิล” หรือ “เลือกรูปบิล” อัปโหลดต้นฉบับผ่าน signed upload ไป private Storage และอ่านรูปภาษาไทย/อังกฤษบนเครื่องผู้ใช้พร้อมกัน
2. แสดงภาพตัวอย่างที่ขยายได้คู่กับฉบับร่าง: วันที่ ผู้รับซื้อ เลขบิล น้ำหนักสุทธิ ราคาต่อกิโลกรัม และรายการหัก ตรวจช่องขาด/ความมั่นใจต่ำ และเทียบยอดสุทธิที่อ่านกับยอดคำนวณ แก้ก่อนยืนยันได้ทุกช่อง ถ้าอ่านไม่ได้/เกิน 45 วินาทีหรือกดข้าม ให้อ่านจากรูปและกรอกเองต่อได้
3. เลือกไม่มีค่าแรง, รายวัน หรือรายน้ำหนัก รายวันรองรับหลายคนและครึ่งวัน รายน้ำหนักใช้กิโลกรัมจากบิลและอัตราบาทต่อตัน โดยแก้ฐานน้ำหนักได้ จำสวน/ผู้รับซื้อครั้งล่าสุด และชื่อ/อัตราคนงาน/ทีมที่บันทึกสำเร็จแล้ว
4. แสดงรายรับ ค่าแรงค้างจ่าย และสุทธิหลังค่าแรงก่อนกดยืนยัน พร้อมยืนยันรับเงินขายเต็มจำนวน

ค่าแรงเกิดเป็น **ค่าใช้จ่ายค้างจ่าย** ใน transaction เดียวกับบิล ทำให้ยอดสุทธิรายสวน/รวมลดลงครั้งเดียว การจ่ายเงินจริงยังเป็นงาน Phase 5 รายการหักบนบิลกับค่าแรงเป็นคนละส่วน ถ้ามีค่าแรงถูกหักในบิลแล้วต้องตรวจไม่ลงซ้ำ

## การเก็บข้อมูลและความล้มเหลว

- เพิ่ม migration `20261021060717_receipt_first_sales_labor.sql` เฉพาะตาราง `sale_labor` และ `labor_profiles` พร้อม owner RLS และสิทธิ์อ่าน ไม่มีการลบ/แปลงข้อมูล production เดิม รายการขายเก่าที่ไม่มีค่าแรงยังอ่านได้
- Server คำนวณจำนวนเต็ม: 3,500 กก. × 1,000 บาท/ตัน = 3,500 บาท; ครึ่งวัน × 400 บาท = 200 บาท เก็บฐานน้ำหนัก/ครึ่งวัน อัตรา และยอดจริงแยกกัน
- เมื่อ upload ตอบล้มเหลว ให้ server ตรวจไฟล์จริงอีกครั้งก่อนตัดสินว่าส่งไม่ถึง ป้องกันกรณีไฟล์ถึง Storage แล้วแต่คำตอบหาย การกดซ้ำไม่ทับต้นฉบับ การบันทึกผิดพลาดไม่ล้างข้อมูลที่กรอกหรือใช้รูปใหม่ทิ้ง
- บันทึกขาย ค่าแรง metadata รูป audit และ idempotency ภายใน transaction เดียวกัน รูปที่ไม่ผูกยังใช้ pending/orphan policy เดิม: หมดอายุ 24 ชั่วโมงและเก็บกวาดในคำขอ upload ถัดไป
- OCR draft อยู่ใน React state ของฟอร์ม ไม่เขียน SQL จนยืนยัน โมเดลภาษา cache ใน IndexedDB ไม่ใช้ข้อมูลเบราว์เซอร์เป็นบัญชีหลัก

## OCR และ HEIC

ใช้ `tesseract.js@7.0.0` กับโมเดลไทย/อังกฤษ pinned `@tesseract.js-data/*@1.0.0` สคริปต์ `prepare-ocr-assets.ts` คัดลอก worker/WASM/โมเดลจาก dependencies ไป `public/ocr` เมื่อ install/dev/build ไม่ดาวน์โหลดจาก CDN ระหว่างอ่านบิล และไม่ส่งรูปไปผู้ให้บริการ OCR ภายนอก

HEIC/HEIF ใช้ `heic-to@1.6.6` แปลงสำเนาสำหรับ preview/OCR ในเบราว์เซอร์เท่านั้น ต้นฉบับไม่ถูกบีบอัดหรือแทนที่ ใบอนุญาต/แหล่งที่มาของ libraries อยู่ใน `public/licenses/ocr-notices.txt` และ license ของ engine เสิร์ฟใต้ `/ocr`

## ผลตรวจ

- Model เดิม 4/4; unit/API/CLI tests 28/28 กับ PostgreSQL/Auth/REST/Storage จริงใน isolated localhost test stack
- ตรวจ transaction rollback เมื่อสร้าง profile ล้มเหลวกลางทาง แล้ว retry สำเร็จโดยไม่สร้าง sale/labor/receipt ซ้ำ
- ตรวจ owner reads, outsider RLS, anon denial และปฏิเสธ authenticated direct writes ของสองตารางใหม่
- Chromium targeted flow ผ่าน: OCR ภาษาไทยจริงเติมน้ำหนัก 3,500.000 ราคา 5.00 เลขบิล และหัก 500.00 → ตรวจข้อมูล → ค่าแรง 1,000 บาท/ตัน → บันทึก ใช้ประมาณ 6.4 วินาทีในเครื่องทดสอบ และเปิดรูปต้นฉบับจาก Storage จริงได้
- HEIC fixture จริงแปลง preview ได้, ข้าม OCR ได้, ค่าแรงครึ่งวัน/จำอัตราหลัง reload และ retry หลัง save ล้มเหลวผ่าน targeted test
- Typecheck, format check และ production build ผ่าน; full Chromium suite ผ่าน 5/5 รวม flow หลัก, HEIC/รายวัน/คำตอบ upload หาย/save ล้มเหลว/จำอัตรา และ UI/Three.js เดิม รอบสุดท้าย flow บิลตัวอย่างใช้ 7.139 วินาที (รอบอื่นประมาณ 4.7–6.4 วินาที)
- API ส่งวันที่ธุรกิจเป็น `YYYY-MM-DD` และ browser ตรวจวันที่ภาษาไทยในประวัติขาย ป้องกัน `Invalid Date`

ผลจับเวลาเป็น **automation กับภาพบิลสังเคราะห์ที่ชัดใน local stack** ยังไม่ได้ยืนยันเป้าหมาย 1 นาทีสำหรับผู้ใช้กับรูปบิลจริงบน iPhone/Safari หรือเน็ตมือถือ โมเดลต้องโหลดครั้งแรก และ OCR ฟรีอาจอ่านผิด จึงต้องตรวจยืนยันก่อนเขียนบัญชีเสมอ
