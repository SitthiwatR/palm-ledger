# Phase 10 — OCR และการตรวจรับการใช้งาน

ผู้ใช้ให้พัก Phase 9 แล้วเดิน Phase 10 เพื่อเริ่มทดลองใช้และเก็บรายละเอียดทีละส่วน งานพัฒนาและผล automation แยกจากการรับงานบนอุปกรณ์จริง ไม่ถือว่า Vercel Ready หรือ Chromium ผ่านแทน Safari/iPhone จริง

## วิธีอ่านบิลที่เลือก

หลังผู้ใช้ถามว่าควรใช้ OCR หรือไม่ ปรับ **แนบรูปแล้วกรอกเองเป็นค่าเริ่มต้น** เพราะข้อมูลเงินจากบิลแบบที่สองยังอ่านผิด OCR อยู่ใน “ตัวช่วยอ่านบิล (OCR) · เลือกใช้ได้” และไม่โหลด worker/โมเดลจนกดอ่าน ไม่ต้องรอ OCR เพื่อกรอกหรือบันทึก นี่เป็นค่าเริ่มต้นที่แก้กลับได้ ยังไม่ได้รับคำสั่งให้ถอด OCR ทั้งหมดหรือถือว่าคุณภาพ extraction ผ่านการรับงาน

คง **OCR ฟรีในเบราว์เซอร์** ตามที่ผู้ใช้เลือก ไม่เพิ่ม API key หรือส่งรูปให้ผู้ให้บริการ vision ภายนอก ใช้ Tesseract.js 7.0.0 และโมเดลไทย/อังกฤษที่ตรึงเวอร์ชันเดิม อ่านบนเครื่องผู้ใช้ รูปต้นฉบับอัปโหลดตรงไป private Supabase Storage เดิม

รอบนี้เพิ่มการอ่านซ้ำเมื่อยังไม่พบยอดพิมพ์บนบิลหรือยอดไม่ตรงสูตร หลังภาพขาวดำและภาพสีที่ปรับแนวแล้ว ยังอ่านภาพสีเดิมได้เพื่อไม่ให้การลบเส้นตารางทำตัวเลขหาย เลขที่อยู่/เลขทะเบียนรถไม่ถูกใช้เป็นเลขบิล แยกวันที่ที่อยู่ข้างเลขบิลก่อนรวมช่องว่าง OCR และรองรับยอด “เป็นเงิน” กับชื่อลานเทปาล์ม

เจ้าของหมุนรูปครั้งละ 90° และเลือกช่วงบิลด้วย slider ที่ใช้ได้ด้วยนิ้ว/คีย์บอร์ด โดยต้องเหลือชื่อช่องและตัวเลขครบ ภาพส่วนนี้ใช้เฉพาะอ่านซ้ำ **ไม่แก้/แทนรูปต้นฉบับ** ผลอ่านใหม่แสดงแยกไว้ให้เลือกใช้หรือเก็บข้อมูลที่แก้เอง การอ่านซ้ำไม่ขอ upload URL ใหม่ ไม่สร้างขาย/ค่าแรง และยกเลิกกลับกรอกเองได้

OCR แบบเลือกใช้มีขีดจำกัดเวลา 45 วินาที คำขอ API/อัปโหลดรอได้ไม่เกิน 60 วินาที การไม่ใช้ OCR ไม่ขัดขวางการเก็บต้นฉบับ การอัปโหลดที่ตอบกลับหลุดยังตรวจว่าไฟล์ถึงแล้วก่อนรายงานผล การลองบันทึกซ้ำใช้ idempotency key เดิมเมื่อ payload เดิม ฟอร์มไม่แจ้งสำเร็จก่อน backend ตอบ

### ทางเลือกที่ประเมิน

| ทางเลือก | ความเป็นส่วนตัว/ค่าใช้จ่าย | ผลการเลือก |
| --- | --- | --- |
| Tesseract เดิม + อ่านซ้ำ/เลือกช่วง/แก้ parser | อ่านในเครื่อง ไม่มีค่าบริการ OCR ต่อบิล; ยังใช้โควตา hosting/Storage | ใช้ต่อและวัดกับบิลจริงก่อน–หลัง |
| โมเดล `4.0.0_best_int` จาก dependencies เดิม | อ่านในเครื่อง/Apache 2.0; อังกฤษ gzip เล็กลงประมาณ 11 MiB → 2.9 MiB | ทดลองแบบแยกใน benchmark แล้ว ไม่เพิ่มความแม่นยำของ draft ในสองรูปเดิม จึงไม่เปลี่ยนโมเดลที่ผู้ใช้ใช้อยู่ |
| Native TextDetector | ไม่ต้องส่งรูปออก แต่ API ฝั่ง Chrome ยังมีข้อจำกัดและไม่ใช่ฐานรองรับ Safari ที่พิสูจน์แล้ว | ไม่ใช้เป็นวิธีหลัก |
| PaddleOCR | มี toolkit/โมเดลหลายภาษา ต้องประเมิน runtime/model/license ของรุ่นที่จะใช้และเครื่องจริงใหม่ | ยังไม่มีหลักฐานว่าแทนที่บน Safari ได้ดีขึ้น ไม่เพิ่ม server/model โดยเดา |
| Cloud vision/AI | ต้องส่งบิลให้ผู้ให้บริการ มีเงื่อนไขข้อมูลและโควตา/ค่าใช้จ่าย | ผู้ใช้ยังไม่เลือกหรืออนุมัติ จึงไม่เรียกบริการ |

แหล่งทางการตรวจวันที่ 22 ตุลาคม 2569: [Tesseract.js](https://github.com/naptha/tesseract.js), [โมเดล](https://github.com/naptha/tessdata), [Shape Detection](https://developer.chrome.com/docs/capabilities/shape-detection), [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR)

### วัดกับรูปส่วนตัว

ใช้รูปต้นฉบับ JPEG สองรูปแบบที่มีอยู่แล้ว อ่านอย่างเดียวและตรวจ SHA-256 แล้วนำมาทดสอบกับฐาน local แยก ไม่มีการสร้าง fixture บน production ไม่ commit รูป ข้อความ OCR หรือเลขบิลจริง ตัวเลขในรายงานเป็นสถิติ ไม่ใช่ข้อมูลต้นฉบับ

Ground truth รอบนี้ตรวจวันที่ เลขบิล น้ำหนัก ราคา และยอดพิมพ์ (5 ช่องต่อรูป) ไม่ใช้คะแนนนี้รับรองชื่อผู้รับซื้อ รายการหักทุกแบบ หรือเวลาทั้ง flow บนอุปกรณ์จริง

- Baseline ก่อนแก้ extraction: รูป A 5/5 ช่อง, 10.78 วินาที; รูป B 2/5 ช่อง, 10.03 วินาที ต้องแก้ 3 ช่อง
- ทดลองโมเดล compact ก่อนแก้ pipeline: A 5/5, 11.61 วินาที; B 2/5, 11.99 วินาที ไม่ได้ลดจำนวนช่องแก้
- ผลหลังแก้/ยังอ่านอัตโนมัติในรอบเทียบ: A 5/5, 10.63 วินาที; B 3/5, 13.45 วินาที เลขบิลดีขึ้น แต่ราคา/ยอดพิมพ์ยังต้องแก้ 2 ช่อง
- ทดลองเลือกช่วงใน B: 3/5, 22.93 วินาทีรวมอ่านครั้งแรกและอ่านช่วงซ้ำ ไม่ได้แก้ปัญหาตัวเลขบนเส้นตาราง จึงไม่รับรองว่า crop ช่วยได้ทุกใบ
- หลังเปลี่ยนเป็นกรอกเอง/OCR แบบเลือกใช้ รอบเต็ม: A 5/5, 13.66 วินาที; B 3/5, 13.75 วินาที รวม upload/กดอ่านเสริม/ใช้ draft ผ่าน automation ไม่ใช่เวลามนุษย์หรือเวลาถึงฟอร์ม manual อย่างเดียว ดูผลรวมใน handoff

เป็นผลบน Chromium/cloud ไม่ใช่การรับรองบิลทุกประเภท ค่าบริการ OCR 0 บาทต่อบิล ไม่รวมโควตา data transfer/Storage และค่าแพ็กเกจโฮสต์

ใช้ manifest JSON **นอก repository** เมื่อมีบิลเพิ่ม โดยแต่ละรายการมี `path`, `selection` (ถ้าต้องการประเมินการหมุน/เลือกช่วงด้วย `turns`, `top/right/bottom/left` เป็นเปอร์เซ็นต์) และ `expected` ของ `saleDate`, `buyer`, `invoiceNumber`, `weightKg`, `priceBahtPerKg`, `printedNetBaht` (ละช่องที่ยังไม่มี ground truth ได้):

```sh
OCR_RECEIPTS_MANIFEST=/absolute/private/manifest.json TEST_APP_MODE=production npm run test:browser -- --grep 'Phase 10 reports'
```

รายงานเฉพาะ accuracy รายช่อง จำนวนช่องแก้ และเวลาถึง draft ไม่มีการยืนยันขาย ปิด screenshot/trace/video อัตโนมัติสำหรับรูปส่วนตัว `OCR_MODEL_VARIANT=best_int` ใช้เปลี่ยนโมเดลเฉพาะ benchmark ผ่าน browser route ไม่เปลี่ยน production; `OCR_DEBUG_TEXT=1` เลือกเก็บข้อความไว้ใน `/tmp/palm-private-ocr-N.txt` แบบสิทธิ์ 0600 สำหรับวิเคราะห์ในเครื่องเท่านั้น ห้ามนำไฟล์หรือ test artifacts เหล่านี้ขึ้น Git/บริการสาธารณะ

## โฮสต์และ Auth ที่ตรวจจริง

- ใช้ Vercel project/team เดิม, Next.js API/cookies และ Session pooler/TLS เดิม ไม่เปลี่ยน credentials หรือ encryption key ทดสอบ private JPEG/PNG/WebP/HEIC/HEIF ผ่าน API และ HEIC preview ใน browser แยกจาก iPhone จริง
- Supabase project `feotpdylvprtihgklndj` เป็น ACTIVE_HEALTHY, PostgreSQL 17.11; organization เป็น Free โควตาตาม [pricing](https://supabase.com/pricing): DB 500 MB, Storage 1 GB, egress 5 GB และ cached egress 5 GB; Free อาจพักหลังไม่ใช้งานหนึ่งสัปดาห์ ไม่มี SLA สำหรับงานนี้
- [Vercel Hobby](https://vercel.com/docs/plans/hobby) จำกัด personal/non-commercial จึงยังไม่รับรองว่างานบัญชีสวนเชิงธุรกิจใช้ Free ได้ การอ่านข้อมูลผ่าน connector ไม่ได้ยืนยัน billing tier ของทีม ห้ามอ้างว่าทุกอย่างฟรีหรือเปลี่ยนแพ็กเกจเสียเงินเอง ต้องยืนยันแพ็กเกจที่อนุญาตก่อนเปิดใช้งานเชิงธุรกิจ
- **พบข้อค้างจริง:** GET `/auth/v1/settings` รายงาน `disable_signup: false`, email provider เปิดอยู่ แม้ API แอปจะยอมเฉพาะ owner และ RLS ป้องกัน ledger อยู่ ต้องปิด “Allow new users to sign up” ใน [Supabase Auth](https://supabase.com/dashboard/project/feotpdylvprtihgklndj/auth/providers) แล้วรัน `scripts/check-auth.ts --public-settings` เพื่ออ่าน settings ยืนยัน `true` เครื่องมือ connector ไม่มีคำสั่งแก้ Auth config และ CLI ไม่มี management access token จึงไม่แก้ด้วยการข้ามสิทธิ์ ไม่สร้างบัญชีทดสอบบน production
- ตรวจ changelog ล่าสุด: การเลิก CBC TLS 1.2 บาง cipher เริ่มเร็วสุด 10 พฤศจิกายน 2569 ไม่ต้องปิด TLS verification; ใช้ browser/Node ที่รองรับ TLS ปัจจุบัน ดู [ประกาศ](https://supabase.com/changelog/cbc-tls-ciphers-deprecated)

## รายการตรวจ iPhone/Safari จริง

บันทึก iPhone รุ่น / iOS / Safari / วันที่ / เครือข่าย / รูปแบบบิลและเวลาจริงแต่ละรอบ ควรลองบิลหลายใบอย่างน้อยสองรูปแบบที่ใช้งาน รวมภาพเอียง แสงน้อย และ HEIC ต้นฉบับ อย่าสร้างข้อมูลทดสอบใน production; ใช้ staging กับฐาน/Storage แยก หรือข้อมูลธุรกิจจริงที่เจ้าของตั้งใจบันทึกเท่านั้น

- [ ] Login ด้วย username เดิม แสดง/ซ่อนรหัสผ่าน ไม่เปลี่ยนค่า เมื่อ logout/ผู้ดูแล reset แล้ว session เก่าเข้าไม่ได้
- [ ] เพิ่มสวน/ยอดยกมา เปิดรูปบิลจากกล้องและคลังภาพ HEIC/HEIF ให้ดูต้นฉบับหลังบันทึกได้
- [ ] จับเวลาถ่าย/อัปโหลด → ตรวจแก้ → ค่าแรง → ยืนยัน เป้าหมาย 1 นาที บันทึกช่องที่ผิด/ต้องแก้จริง ไม่ใช้เวลา OCR อย่างเดียวแทน
- [ ] หมุน/เลือกช่วงอ่านใหม่ ยกเลิกกลางคันและเลือกเก็บข้อมูลที่แก้ไว้ได้ ยอดอ่านไม่ตรงต้องเตือน และไม่มีรายการขายก่อนยืนยัน
- [ ] ค่าแรงผูกบิล/ทีมแยกบิลไม่ซ้ำ ปุ๋ยใช้จริงลงถูกสวน จ่ายบางส่วน ยกเลิกจ่ายผิดและลงใหม่ ค้างเปลี่ยนแต่สุทธิไม่หักซ้ำ
- [ ] ดูยอดรวม/แยกสวน/รายการย้อนหลัง/รายงาน แก้ต้นทางและตรวจประวัติแล้ว reload ยังตรง
- [ ] หน้ากว้างประมาณ 390 px และแนวนอน ไม่มี overflow; เปิดคีย์บอร์ดแล้วเลื่อนถึงปุ่มได้ ปิด dialog/focus ถูกต้อง เปิด Reduce Motion แล้วฉาก/ฟอร์มยังใช้ได้
- [ ] เน็ตช้า/หลุดระหว่างอัปโหลด อ่าน และยืนยัน ฟอร์มไม่หาย ไม่แจ้งสำเร็จล่วงหน้า ลองใหม่ไม่สร้างรายการซ้ำ
- [ ] ดาวน์โหลดชุดสำรองเข้ารหัสรวมรูป ตรวจ preview และกู้ลง Supabase ใหม่ที่ว่าง ตรวจบัญชีเดิม/ยอด/รูป SHA ก่อนเลือกใช้เป้าหมายใหม่ (ไม่กู้ทับข้อมูลจริง)

WebKit automation เป็นหลักฐานคนละประเภท รอบนี้ install ถูก policy ปฏิเสธที่ `cdn.playwright.dev`/`playwright.download.prss.microsoft.com` จึงยังไม่มีผล WebKit และไม่มี Safari/iPhone จริง การพัก automatic backup Phase 9 เป็นการตัดสินใจผู้ใช้ ไม่ใช่หลักฐานว่า RPO รายวันผ่านแล้ว
